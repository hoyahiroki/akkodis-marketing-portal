## 1. 方針転換 —「AI機能ありき」から「SharePoint既存パーツ(L1)でできるものから」へ

初版「次フェーズ着手案」は **AI検索を Must（入口）に置き、AIネイティブ6機能を主役に据える**構成だった。SharePoint実装マストの差戻しを受け、**優先順位を反転**する。

- **転換前（初版）**: 「解くべき課題 → それに効く AI 機能」を起点に設計。実装基盤は後で載せる想定。
- **転換後（v2）**: 「**SharePoint の既存パーツ（L1）で今すぐ作れるもの**」を起点に据える。標準 web part・リスト・ライブラリ・Microsoft Search で成立する構成を土台にし、それを超える機能は実装階層を明示して費用・ライセンス・ガバナンスの判断に上げる。

この反転が妥当な理由は、**最重要3課題（B-1／G-2／CA-1）の土台が、いずれも L1（既存パーツ）で着手できる**という見立てにある。逆に、社長指定を含む AI6機能の多くは L2 以上（追加ライセンス依存）であり、テナントの実ライセンスが未確定のまま設計に入ると手戻りが生じる。

### 1-1. 実装階層 L1〜L4 の定義（本書共通）

| 階層 | 定義 | 追加ライセンス／許可 | 位置づけ |
|---|---|---|---|
| **L1** | SharePoint 標準の既存パーツ（OOB）。コミュニケーションサイト、標準 web part（クイックリンク／ハイライトされたコンテンツ／検索ボックス等）、ドキュメントライブラリ、Microsoft Lists、Microsoft Search、メタデータ列・コンテンツタイプ | 原則不要（標準 M365 の範囲） | **最優先**。費用・ガバナンス負荷が最小 |
| **L2** | ローコード／付加ライセンス系。Power Platform（Power Automate／Power Apps）、Microsoft 365 Copilot、Copilot Studio、SharePoint Premium（旧 Syntex） | 追加ライセンス＋管理者ポリシーが前提 | **条件付き**。F0 のライセンス確定後に採否 |
| **L3** | カスタム開発。SPFx（SharePoint Framework）による独自 web part／拡張、コミュニティ製 SPFx（例: PnP Modern Search） | テナントでの**カスタムコード配置許可**が前提 | **後回し／代替検討**。許可が無ければ L1 代替で設計 |
| **L4** | SharePoint 標準機能・拡張では実現不可 | — | 代替案 or 対象外 |

**結論**: **L1中心のMVPを最短で立ち上げ**、L2以上の AI 機能は F0（ライセンス棚卸し）の結果に応じて段階投入する。次フェーズの最初の仕事は「作ること」ではなく「**テナントで何が使えるかを確定すること**」である。

### 3-3. マッピングの含意（F0反映後）

- **課題直結の土台は L1 で成立する**: 直リンク化（CA-1）／ページ内ナビ（B-1）／Microsoft Search 基本（G-2）／メタデータ設計は、いずれも既存パーツ・サイト所有者レベルで着手できる。**Microsoft Search の管理権限が無くても G-2 は L1 で対応可能**であることが F0 で確定した。
- **L3（SPFx カスタムコード）は不可で確定**: AI-3b（高度ファセット／PnP Modern Search）と AI-1 の高度版 SPFx UI は**選択肢から除外**。G-2 は L1 の標準リファイナー＋メタデータ・ビューで代替する。
- **AI-6 はスコープ外（実装しない）**: 社長判断（2026-07-23）により実装対象から外す。メタデータ運用は MVP-4／AI-4 の手動運用（L1）でカバーし、SharePoint Premium の要否確認も不要とする。
- **残る L2 の AI 機能（AI-1／AI-2／AI-4／AI-5）は見通し良好**: M365 Copilot 全社保有・Power Platform 利用可・Copilot Studio 個人利用可により、いずれも技術的射程内。**唯一の残課題は AI-1／AI-2 の"全社公開許可"** で、これは F4（L2拡張）着手時にIT確認する（MVP非ブロッカー）。

## 4. MVP案（L1の4点）

F0 で確定した L1 の範囲を前提に、**最重要課題に直結し、追加ライセンス無しで着手できる L1 の4点**を MVP とする。いずれも既存パーツで実装でき、費用とガバナンス負荷が最小である。

| # | MVP項目 | 解決する課題 | 想定する L1 実装 | 期待効果 |
|---|---|---|---|---|
| 1 | **キャンディデート資料の直リンク化** | **CA-1** | クイックリンク web part／共有リンクで資料へ直接到達。「各チームに連絡」を直リンク＋保管場所明示に置換 | 「見つからず問い合わせ」の即時解消。クイックウィン（§5） |
| 2 | **ブランドライブラリ再構成＋ページ内ナビ** | **B-1**／**B-2** | 長大な単一ページを、目的別セクション＋セクションアンカー／目次で再構成。ガイドライン約10本を粒度・目的で束ね直す | 最多利用ページ（319名）の到達性改善。効果が最も広く届く |
| 3 | **Microsoft Search 基本＋検索/ハイライト web part 設置** | **G-2**／**U-2** | 各ページ上部に検索ボックス web part、ハイライトされたコンテンツ web part を配置し、標準の意味検索を活用（**サイト所有者レベルで完結・検索管理権限不要**＝F0確定） | 「見つからない→メール検索」の入口を是正 |
| 4 | **ライブラリのメタデータ列・コンテンツタイプ設計** | **B-4**／**C-2**（土台） | 資料に対象／言語／種別／版／更新日のメタデータ列を設計・付与。コンテンツタイプで統制。**付与は手動運用**（AI-6 自動付与はスコープ外＝§2-3） | 検索・絞り込み・G-2 の代替ファセット（フィルタ/グループ化ビュー）の**土台**。単独でも走査性が向上 |

> MVP は「**まず L1 で価値を出す**」方針。**F0 実施結果（§2-3）により、この L1 4点はすべて追加ライセンス・検索管理権限・カスタムコードなしで着手可能なことが確定**した。L2 が要る AI 機能（AI-1・AI-2・AI-4・AI-5）は MVP 稼働後に段階投入する（高度ファセットは SPFx 不可のため標準リファイナー＋メタデータ・ビューで代替、AIチェッカーはガイドライン集約＋Copilot Q&A の簡易版から）。AI-6 は実装しない。

## 5. クイックウィン（直リンク化・費用ゼロ）

**最優先のクイックウィンは MVP-1「キャンディデート資料の直リンク化」（CA-1）**である。

- **現状**: キャンディデート向けページのマスター資料が「会社説明資料は各チームで管理。必要な場合は各チームまで直接ご連絡ください」で完結し、資料への直リンク／ダウンロードが無い（分析レポート §1-4）。これがユーザー指摘「見つからなくてわざわざメールを検索したり」を**ポータル側が誘発している典型例**。
- **是正**: 資料の保管場所（ドキュメントライブラリ）を明示し、**クイックリンク web part／共有リンクで直接到達**できるようにする。
- **なぜクイックウィンか**: **L1（既存パーツ）・費用ゼロ・PoC不要**で実装でき、最短でユーザー指摘（メール検索）を潰せる。効果は高く、コストは低い（分析レポート §4-1・§4-2）。
- **着手方針（2026-07-23 確定）**: 費用ゼロ・L1 だが、**単独での先行着手はせず、MVP-1 として本体スコープ内でまとめて対応**する（社長判断・§6-2 の③）。効果とコストの評価は変わらず、MVP の中で最優先実装項目に位置づける。

**併せて着手できる低コスト L1 クイックウィン**（分析レポート §4-2）: B-6（ブランドライブラリ冒頭見出しの黄色マーカー統一）／B-5（ラベルの無いアイコンカードへの説明付与）／P-1（Akkodis ASP Team の余分な画像枠の除去・差し替え。要現物確認）／G-4（ナビの「編集 のナビゲーション」が一般ユーザー表示に露出していないかの確認）／B-4・C-2（資料の命名規則・更新日・対象の付与）。いずれも既存パーツ範囲の是正で完結する。
